# VoxaNex — WebRTC STUN/TURN Media Relay Deployment & Architecture Guide (Phase 5)

This guide documents the WebRTC voice & video media architecture for VoxaNex, including STUN/TURN topology, NAT traversal mechanics, credentials security, and operational constraints.

---

## 1. WebRTC Architecture Overview

VoxaNex uses browser-native WebRTC (`RTCPeerConnection`, `getUserMedia`) for real-time 1-on-1 audio and video calling between matched participants and direct contacts.

### Signaling Stack:
- **Transport**: Authenticated server-sent event (SSE) streams (`/api/webrtc/signaling/:userId/events`).
- **Authorization**: Validated server-side before call initiation, acceptance, or signal dispatch.
- **Relayed Signals**:
  - `offer`: SDP session description generated by the initiator upon call acceptance.
  - `answer`: SDP session description generated by the recipient.
  - `ice_candidate`: Incremental ICE host, srflx (STUN), and relay (TURN) candidate candidates.
  - `mute_state`: Audio / camera track toggle indicators.
  - `hangup`: Explicit call termination signal.

## 2. STUN & TURN NAT Traversal Topology

### Default STUN:
In direct peer-to-peer conditions (Full Cone NAT, Restricted Cone NAT), STUN queries determine the client's public reflexive IP and port:
- `stun:stun.l.google.com:19302`
- `stun:stun1.l.google.com:19302`
- `stun:stun2.l.google.com:19302`

STUN carries **zero media data**; it only discovers public IP/port mappings.

### TURN Relay (Symmetric NAT / Firewall Traversal):
When one or both peers are behind symmetric NAT (common on mobile 4G/5G mobile carriers in Bangladesh like Grameenphone, Robi, Banglalink, and corporate Wi-Fi), direct P2P connections cannot be established through STUN alone. In this case, ICE negotiation falls back to a TURN relay server.

### Supported TURN Providers:
1. **Coturn (Self-Hosted)**:
   - High performance, open-source C-based STUN/TURN server.
   - Recommended deployment on a low-latency VPS close to South Asia (e.g., Singapore, India, or Dhaka).
2. **Metered.ca / Twilio Network Traversal / Cloudflare Calls**:
   - Managed global TURN service with automatic geographical routing.

## 3. Environment Variables Configuration

Configure the following variables in your server environment (or `.env` file):

```bash
# Optional TURN server configuration for symmetric NAT traversal
# Comma-separated URLs (UDP and secure TLS TCP recommended)
TURN_SERVER_URL="turn:turn.yourdomain.com:3478?transport=udp,turns:turn.yourdomain.com:5349?transport=tcp"

# Short-lived or provisioned TURN user credentials
TURN_USERNAME="voxanex_turn_user"
TURN_CREDENTIAL="your_secure_turn_password_or_token"
```

### Security & Secret Protection:
- **Never expose master TURN credentials in client bundles**: The frontend queries `GET /api/webrtc/ice-servers`. The backend endpoint reads the server-side environment variables and formats the ICE configuration for the authenticated session.
- **Short-Lived Ephemeral Credentials**: For production Coturn deployments, implement the REST API time-limited credential mechanism (`HMAC-SHA1(username + expiry, secret)`).

## 4. Operational Requirements & Bandwidth

| Media Kind | Resolution / Codec | Target Bitrate | Latency Target |
| :--- | :--- | :--- | :--- |
| **Audio Only** | Opus (48 kHz) | 24 - 40 kbps | < 150 ms |
| **Video Call** | VP8 / VP9 / H.264 (720p HD) | 400 - 1200 kbps | < 250 ms |

### Network Failure & Reconnection:
- WebRTC `oniceconnectionstatechange` triggers automated reconnection state displays (`connecting`, `connected`, `disconnected`, `failed`).
- When a peer loses network connectivity for > 10 seconds, the session flags a network interruption and offers retry or safe termination.
- All media streams and hardware tracks are explicitly released on call hangup to prevent background microphone or webcam capture.
